二、新电脑完整复现
----------------
系统：Ubuntu 24.04 amd64/arm64；ROS 2 Jazzy Desktop。先按 ROS 官方说明配置 apt 源，
再执行：

  sudo apt update
  sudo apt install -y git build-essential python3-pip python3-rosdep \
    python3-colcon-common-extensions python3-opencv \
    ros-jazzy-desktop ros-jazzy-slam-toolbox ros-jazzy-navigation2 \
    ros-jazzy-nav2-bringup ros-jazzy-cv-bridge ros-jazzy-tf2-sensor-msgs \
    ros-jazzy-pointcloud-to-laserscan ros-jazzy-robot-state-publisher \
    ros-jazzy-xacro ros-jazzy-rviz2 ros-jazzy-rosbag2 ros-jazzy-joy \
    ros-jazzy-ros-gz

首次使用 rosdep：

  sudo rosdep init        # 如果提示 already initialized 可忽略
  rosdep update

获取并构建：

  git clone <仓库地址> ~/wakula
  cd ~/wakula
  source /opt/ros/jazzy/setup.bash
  rosdep install --from-paths src --ignore-src -r -y
  ./scripts/build.sh
  source install/setup.bash

建议把下行加入 ~/.bashrc（路径不同请修改）：

  source /opt/ros/jazzy/setup.bash
  source ~/wakula/install/setup.bash

VS Code：安装 Visual Studio Code 后，打开 ~/wakula。建议 Python、Pylance、C/C++、
CMake Tools、XML、YAML、ROS 插件；项目已有 .vscode/settings.json 和 tasks.json。

三、启动前必须由外部提供
--------------------
最低导航输入：
  /scan      sensor_msgs/msg/LaserScan
  /odom      nav_msgs/msg/Odometry
  odom -> base_link TF

SLAM 产生 map -> odom。启用地形感知还需：
  RGB Image
  PointCloud2（x/y/z，米）
  base_link 到传感器 frame 的 TF

当前仓库不会生成真实里程计或驱动电机。

四、常用启动命令
--------------
正常联调只需三个运行终端、三个命令：

  cd ~/wakula
  source /opt/ros/jazzy/setup.bash
  source install/setup.bash
  # 终端 1：仅 Gazebo 场地、测试载体、传感器和运动接口
  ros2 launch quadruped_gazebo robocon_field.launch.py
  # 终端 2：仅核心 SLAM、Nav2、OpenCV、点云和 RViz
  ros2 launch slam slam.launch.py
  # 终端 3：独立自主探索与越障任务；启动即运行
  ros2 launch slam autonomous_navigation.launch.py

第三条不启动或关闭 SLAM、Nav2、OpenCV、RViz、Gazebo；现实传感器和 Gazebo 传感器接口
一致。在第三个终端按 Ctrl-C，会先锁住自动导航速度并停车，再取消 Action；第一、二条
进程继续运行。键盘或手柄持续发布时仍可人工接管，不需要重新启动第三条。

第一条在 GUI 模式下会自动打开 `Wakula Simulation Keyboard` 窗口；点击该窗口后使用
i/k 前后、j/l 原地旋转、任意其他键停车。无需运行第四条键盘命令。

真机要求运动组提供 /traverse_obstacle Action 服务端。仿真时第三个命令检测到 /clock 后
自动启动通用测试狗的 Action 替身，不再需要第四个常规命令。Gazebo 场地仍独立启动：

  ros2 launch quadruped_gazebo robocon_field.launch.py

在线探索使用 16 m × 8 m 滚动全局代价地图；任务层只容忍机器人超出最新 SLAM 栅格
边界 0.30 m 以内的短暂发布滞后，超过后仍停在 WAITING_FOR_MAP。该策略避免仿真越障
落点仅越界几厘米就永久停止，同时不会放行定位大跳变。

以下命令只供运动控制开发者脱离自主任务单独验证 Action 合同：

  ros2 launch quadruped_gazebo sim_traversal_controller.launch.py

仿真中 slam.launch.py 的启动摘要必须包含：
  simulation_detected=true, use_sim_time=true, robot_model=false
入口会重试检测 /clock。若现场仍未显示上述值，停止该算法进程并显式运行：
  ros2 launch slam slam_sim.launch.py
然后再启动独立自主 launch；仿真传感器时间与算法系统时间不一致时会安全输出零速。

无相机：

  ros2 launch slam slam.launch.py vision:=false

无 RViz：

  ros2 launch slam slam.launch.py rviz:=false

回放 bag：

  ros2 launch slam slam.launch.py use_sim_time:=true
  ros2 bag play <bag目录> --clock

设备 profile：

  ros2 launch slam slam.launch.py sensor_profile:=orbbec_gemini2

自定义话题：

  ros2 launch slam slam.launch.py \
    scan_topic:=/lidar/scan odom_topic:=/localization/odom \
    camera_topic:=/camera/color/image_raw point_cloud_topic:=/camera/depth/points

只启动感知与速度门，不启动 SLAM/Nav2：

  ros2 launch quadruped_bringup bringup.launch.py

Xbox 手柄（使用独立 launch，刻意不加入 slam.launch.py）：

  ros2 launch quadruped_teleop xbox_teleop.launch.py

手柄启动后，十字键上等价于另开终端执行
`ros2 launch slam autonomous_navigation.launch.py`，十字键下等价于在该自主任务终端按
Ctrl-C。自主任务默认不启动；按住不会重复触发。下键只结束由当前 xbox_teleop 创建的任务，
不关闭 Gazebo、核心 slam.launch.py 或其他终端手动启动的自主任务。

Gazebo 比赛参考场地（同样独立，不加入 slam.launch.py）：

  ros2 launch quadruped_gazebo robocon_field.launch.py

无 GUI：

  ros2 launch quadruped_gazebo robocon_field.launch.py gui:=false

只看场地、不生成传感器载体：

  ros2 launch quadruped_gazebo robocon_field.launch.py spawn_test_robot:=false

联合测试须另开终端启动算法，避免重复发布占位 TF：

  ros2 launch slam slam_sim.launch.py

slam_sim.launch.py 不启动 Gazebo，只把核心 slam.launch.py 固定为 use_sim_time=true、
robot_model=false，避免漏参造成仿真时钟不一致或重复 TF。真机仍使用 slam.launch.py。
普通 slam.launch.py 现在也会自动检测运行中的 /clock；首行必须显示
simulation_detected=true、use_sim_time=true、robot_model=false。
这会由算法入口启动 RViz、SLAM Toolbox、Nav2、OpenCV 和点云分析。通用机械狗测试替身已经发布默认
/scan、/odom、odom->base_link、/imu/data、/camera/image_raw、/camera/depth/points，并
提供 lidar_link、camera_link、camera_optical_frame、imu_link 的 TF，不需要额外 remap。
它的腿仅为固定外观，载体保持水平且无动力学碰撞，只用于算法联调；不能验证步态/接触，
直接 /cmd_vel 也可能穿过障碍。仿真 RGB-D 光心位于机头外并向下俯约 14°，避免自身
外观遮住 RGB 或令深度云全部为 Inf；默认 424×240@15 Hz 并关闭传感器可视化，
world 物理时钟为 100 Hz，/clock、关键导航和辅助数据分桥运行，避免 GUI/RViz 同机时
/scan 与 /odom 断流；默认话题不变，真机更换常见分辨率
无需改算法。正式模型可这样一次替换：

  ros2 launch quadruped_gazebo robocon_field.launch.py \
    robot_sdf:=/绝对路径/real_quadruped/model.sdf \
    robot_name:=real_quadruped publish_test_sensor_tf:=false

联合测试中 Gazebo 的终端/窗口必须保持运行；关闭后 RViz 可能仍保留最后一张地图，但数据
已经停止。出现“感知数据无效”先分别执行 ros2 topic hz /scan、/odom 和
/camera/depth/points。当前参考仿真的正常值约为 15 Hz、25~30 Hz 和 15 Hz；地图在运动中
约 4 Hz 发布，扫描匹配最多约 10 Hz，8 cm / 0.08 rad 即可加入新关键帧。

RViz 的 Camera Detection 面板会显示 /vision/annotated_image：青色为 ROI，黄色为当前帧
候选，绿色为多帧稳定结果。标注图使用与 RViz 默认 Image 显示兼容的 RELIABLE QoS；
算法终端会周期打印“[正前方障碍]”；也可单独查看：

  ros2 topic echo /perception/front_obstacle_name

名称以可量测几何为准：10° 坡面显示“主斜坡”，14° 坡面显示“木桥引坡”，其余可显示
T 字形台阶、限高杆、直角绕杆区、砂砾与碎木坑或高墙。仅检测到比赛颜色而点云尚未完成
分类时，会显示“视觉检测到有色比赛障碍（点云待分类）”；这不是程序漏报，也不会冒充已
确认类别。木桥 B、坑区护栏/填料及限高杆支柱会显示接近阶段名称；算法不会读取仿真坐标，
证据不足以区分结构时会明确显示“待确认”。

当前识别回归基线：宽台阶/木桥不会再因占据多数而把入口反报成坑；蓝白限高杆可由多个
蓝色短段合并，并由点云给出约 0.30 m 净空；约 70 mm 立柱即使只占 1～2 个高度格，也会
在原始回波和三维跨度充足时保留。纯 Canny 大框不再猜成 WALL，墙面必须由点云确认。
若标注图显示 `VISION: NONE` 但 `FRONT` 和终端名称正确，表示 OpenCV 没有可证明的颜色
结构，不是点云漏检；视觉只做辅助，不能为追求“每帧都有名字”而放宽成误报。

RViz 地图：白色=已观测自由区，黑色=障碍，灰色=未知区。默认隐藏 TF、网格和实时
LaserScan；顶视图默认跟随 base_link，地图仍固定在 map 坐标，并以 0.25 s 周期发布。
排查时再手动勾选。开放场地初始的白色射线边缘属于探索范围；低速覆盖通道，
每到转角停留并旋转一周，再通过闭环后的黑色墙线重合程度判断 SLAM。地图整体旋转不影响
导航。若出现从机器人向外发散的黑墙，先检查二维雷达是否水平以及 lidar_link TF。
若终端显示“视觉疑似××（点云未确认）”，表示 OpenCV 只触发保守限速，几何类别尚未
得到点云尺度确认。

Nav2 只会在雷达角度/样本/frame、里程计时间/frame/协方差和定位 TF 全部有效后激活。
点云进入局部代价地图前会自动剔除拟合地面和坡面；真机只需保证点云 TF 正确，并用
rosbag 调整 terrain.yaml 的相对地面高度阈值，不要在相机驱动侧重复裁成绝对 z>0。
GUI Gazebo 已自动提供键盘窗口。只有用 `keyboard_teleop:=false` 关闭自动窗口或单独排障时
才运行备用脚本：

  cd ~/wakula
  ./scripts/keyboard_teleop.sh

自动长时间联合回归（只允许对仓库自带 Gazebo 测试狗使用，会主动发布速度）：

  ros2 run quadruped_tools stack_regression --allow-motion --cycles 5 \
    --report reports/stack_regression.json

它验证双向整圈旋转、前进/倒退回环、Nav2 多目标、1 m 绕杆窄通道、不可达目标恢复，
并记录 map/scan/odom/越障引导间隔、闭环误差、错误 READY、ALIGN/READY 边界抖动和核心
进程 CPU/RSS。2026-08-13 入口稳定性复测收到 665 帧 guidance 且错误 READY 为 0；另一次
边界复测进入 READY 6 帧，无小于 0.35 s 的 ALIGN/READY 快速往返。未写 --allow-motion 会
拒绝运行；真机不得用这个命令代替正式测试流程。

保持键盘终端获得焦点，i/k 前后、j/l 原地旋转。不要再把键盘直接 remap 到 /cmd_vel：
自动导航最终速度门也会发布该标准话题，二者会互相覆盖。Gazebo 专用 mux 将
/cmd_vel_teleop 作为短时高优先级输入，统一输出 /cmd_vel_gazebo；真机接口不受影响。

若日志持续出现 Detected jump back in time，先运行 `ros2 topic info /clock --verbose`；通常
是重复启动了两个 Gazebo。每次只能保留一个 robocon_field.launch.py，停止旧实例后重启
Gazebo 和算法。当前 launch 已隔离 Snap VS Code 的 GTK_PATH，`libpthread/GLIBC_PRIVATE`
不应再出现；若使用自定义 launch，仍需清除该变量或改用 Ubuntu 系统终端。
Ubuntu 崩溃窗口可能延迟显示旧报告；核对窗口中的 Date 和最新 ~/.ros/log。最新日志若显示
“rviz2 process has finished cleanly”，可关闭旧弹窗，不要误判为当前算法崩溃。
检查 TF 优先运行 `./scripts/diagnose.sh`。不要使用 `tf2_echo ... | head`：tf2_echo 会持续
输出，head 提前关闭管道时 ROS 2 Jazzy 可能弹出 BrokenPipeError；这不是 SLAM/Nav2 崩溃。
若曾看到 collision_monitor 在 get_subscription_count() 处 SIGSEGV，那是旧版本速度链。
当前版本不再启动该 Jazzy 进程：navigation_speed_gate 直接输出 /cmd_vel，并用 /scan 做
0.22 m 极近距离急停。重新编译并用 slam.launch.py 启动即可。

规则只公布障碍结构尺寸与颜色，尚未公布正式排列坐标。参考 pose 全部集中在
src/quadruped_gazebo/worlds/robocon_obstacle_field.sdf 开头的 REFERENCE LAYOUT；正式坐标
到手后只修改八个 layout_* frame，不修改算法 launch 或参数。

先用 `ros2 topic echo /joy` 核对实际轴/按键下标，再查看 `/cmd_vel_joy`。默认不会接管
`/cmd_vel`；真机阶段增加 twist_mux，将手柄和 Nav2 仲裁结果送入硬件安全层与驱动。
LB 必须在摇杆回中时按下才会解锁；带量按下会被拒绝，需松开并重新按下。轴方向相反时
修改 xbox.yaml 的 linear_x_direction、linear_y_direction 或 angular_z_direction 为 -1.0。
十字键上下默认读取 axes[7]（上 +1、下 -1）；若驱动相反，将 dpad_y_direction 改为 -1.0。
用 `ros2 topic echo /teleop/autonomy_process` 可查看 STOPPED/RUNNING/STOPPING/FAILED。
若手柄断流，节点持续输出零速度；恢复连接后必须先松开并重新按下 LB。

五、快速验收
----------
  ros2 topic hz /scan
  ros2 topic hz /odom
  ros2 topic hz /terrain/features_stamped
  ros2 topic hz /vision/obstacle_stamped
  ros2 topic hz /vision/annotated_image
  ros2 topic echo /perception/front_obstacle_name
  ros2 topic echo /terrain/navigation_mode
  ros2 topic echo /terrain/speed_limit
  ros2 topic echo /terrain/navigation_safety
  ros2 topic echo /traversal/guidance
  ros2 topic echo /traversal/phase
  ros2 run tf2_ros tf2_echo base_link <点云frame>
  ros2 run tf2_ros tf2_echo map base_link
  ./scripts/diagnose.sh

需要定位某个话题由谁发布/订阅时，先查 connect.txt 第二节的节点作用与关键接口，再运行：

  ros2 node list
  ros2 node info /节点名
  ros2 topic info /话题名 --verbose

正常现象：vision=true 时相机短暂缺帧会先等待同步，超过 0.25 s 后自动使用纯点云结果；
点云也缺失或无效才保持 speed_limit=0。识别 CLEAR 且数据持续新鲜后为 1；
越障目标在远处先低速 APPROACH/ALIGN，进入 1.20 m 交接区后为 READY 且速度归零；
POLE 由 Nav2 低速绕杆。相机证据不能触发腿部动作。`/navigation/healthy` 为 false 或
断流时速度门也保持零。只有点云时
使用 vision:=false，决策会自动采用兼容路径。

六、录包与离线评估
----------------
  ./scripts/record_bag.sh
  ros2 bag info bags/<bag名>
  ros2 run quadruped_tools perception_bag_evaluator --help

每种障碍至少采集不同距离、角度、速度、明暗、逆光和背景；还要采集大量无障碍负样本。
视觉集必须额外覆盖全黑/全白、局部阴影、顶灯频闪、金属高光、镜头污渍、运动模糊和
部分遮挡；点云集覆盖黑色/反光表面、深度空洞、孤立及相邻飞点、坡面和砂砾。
标签必须对应传感器时间，不要按观看视频的电脑时间粗略对齐。优先降低坑洞/高墙漏检，
再优化普通类别误报。

七、开发与提交检查
----------------
  ./scripts/build.sh
  source install/setup.bash
  colcon test
  colcon test-result --verbose
  git status --short
  git diff --check

修改算法时同步更新 README.md、instruction.txt、connect.txt、quickstart.txt。新增通信接口先
更新 connect.txt；改变参数或流程更新 instruction.txt；新增启动方式更新 quickstart.txt。
新增模块或修改关键算法时同步维护模块/函数 docstring、参数分组、单位、坐标系、失效行为和
“为何采用该策略”的注释；不要用逐行复述代码的注释制造阅读噪声。

八、真机出来后的接入顺序
--------------------
1. 测量传感器安装位姿并修正 URDF/静态 TF。
2. 启动传感器驱动，通过 profile/remap 对齐 Image、PointCloud2 和 LaserScan。
3. 接入可靠 `/odom` 与 odom->base_link，只验证 SLAM 和 Nav2，不连接电机速度。
4. 录真实 bag，重调点云与 OpenCV，完成准确率统计。
5. 单独开发硬件驱动、状态估计、运动学、步态和安全层，并在台架验证。
6. 底盘能安全消费 `/cmd_vel` 后低速接入 Nav2。
7. 实现现有 /traverse_obstacle Action 的真机服务端与安全控制权切换；不得把收到 Goal
   当作动作完成，只有姿态/接触闭环确认落地后才能返回 success=true。

九、其他团队一键对齐
------------------
硬件/状态估计组交付以下标准接口即可：/scan（LaserScan）、/odom（Odometry）、
odom->base_link、传感器 TF、Image 和 PointCloud2。底盘/运动控制组订阅最终 /cmd_vel
（Twist）；越障控制组实现 /traverse_obstacle 服务端，并以 /terrain/navigation_safety
复核环境有效性。不要把 STEP/CLIMB 或 READY 直接转换成关节动作；READY 只表示入口距离
和对正条件满足，Action Result 才向任务层表达完成/失败。

真机发布自身 URDF/TF 时这样启动：

  ros2 launch slam slam.launch.py robot_model:=false sensor_profile:=generic

全栈稳定后执行只读验收：

  ./scripts/check_integration.sh /camera/image_raw /camera/depth/points

实际话题不同就替换两个参数，或先在 sensor_profiles.yaml 添加设备 profile。检查脚本验证
话题类型、map/odom 到 base_link 的 TF、算法输出和 /cmd_vel 消费者；失败项按 connect.txt
修正。它不发送速度，也不启动硬件。VS Code 命令面板可直接运行同名 ROS 对接检查任务。

十、RK3588 建议
-------------
保持 OpenCV 路径，不启用 YOLO；当前在线档为图像最大宽度 576、处理 5 Hz，点云处理 5 Hz。
独立 Gazebo 测试载体使用 424×240，但真机可先用 640×480 或 640×360，再根据实测余量调整。
确认 CPU/内存余量后再提高分辨率或频率。优先让相机/雷达驱动在硬件侧完成对齐、降采样
和滤波，避免同一份点云被多个节点重复转换。算法侧 `terrain.yaml` 的
transform_max_points 默认把 TF 前原始云限制为 40000 点，几何分析再限制为 12000 点，
Nav2 障碍云最多 1800 点；离线对照时可设为 0，真机算力
不足时应结合 rosbag 准确率逐步降低，不能只凭运行流畅程度调参。
高度栅格分位数已向量化；本机 50 次、每次 20000 点的纯几何基准由约 4.63 s 降到
0.30 s。全栈 x86 实测核心进程峰值约 858 MiB、瞬时约 1.53 个 CPU 核，但 RK3588
仍须单独记录温度、功耗、降频和端到端延迟。无显示器部署可令 vision.yaml 的
publish_annotated_image=false，减少标注图复制和编码；不要为了省算力关闭安全数据链。
