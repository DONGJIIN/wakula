Wakula 后续开发与快速上手指南
=============================

适用对象
--------

本文件面向第一次接触 Wakula 的开发者，目标是在较短时间内完成环境检查、编译、启动、
理解当前进度，并知道下一步应该开发什么。更详细的算法原理见 instruction.txt，完整
通信接口见 com.txt，安装和常用入口见 README.md。


一、当前项目定位
----------------

Wakula 是一个 ROS 2 Jazzy 四足机器人自主导航和越障原型，当前运行平台为：

  操作系统：Ubuntu 24.04
  ROS 版本：ROS 2 Jazzy
  目标计算平台：RK3588
  机器人结构：12 自由度四足
  导航：SLAM Toolbox + Nav2
  视觉：OpenCV HSV、Canny、轮廓和多帧投票
  深度感知：PointCloud2 前方 ROI 地形统计
  控制接口：ros2_control 调试接口 + 预留机器狗 SDK 适配层

软件已经形成“建图定位—路径规划—视觉提示—点云测高—越障决策—速度安全”的完整
上层链路，但尚未包含特定机器狗的硬件 SDK、真实关节力矩控制、MPC/WBC、完整高程图
或足端落脚点规划器。


二、第一次接手时的十分钟流程
----------------------------

1. 打开终端并进入工作空间：

  cd ~/wakula

2. 确认当前 Git 状态：

  git status -sb
  git log --oneline -5

3. 加载 ROS 2 环境：

  source /opt/ros/jazzy/setup.bash

4. 安装缺失依赖：

  ./scripts/bootstrap.sh

5. 编译全部 6 个 ROS 包：

  ./scripts/build.sh

6. 加载本工作空间：

  source install/setup.bash

7. 运行测试：

  colcon test --event-handlers console_direct+
  colcon test-result --verbose

8. 只查看 URDF 模型：

  ros2 launch quadruped_description display.launch.py

9. 无传感器启动完整软件检查进程：

  ros2 launch slam slam.launch.py rviz:=false

  没有 /scan、/odom 和 map -> base_link TF 时，Nav2 会保持未激活并显示等待信息，
  这是安全设计，不是报错。按 Ctrl+C 应正常退出且不产生崩溃报告。

10. 阅读文档：

  README.md              用户入口和总体架构
  instruction.txt       模块作用与算法原理
  com.txt               所有通信名称和接口合同
  DEVELOPMENT_GUIDE.txt 本文件，开发进度和后续路线


三、目录速查
------------

src/quadruped_description
  quadruped.urdf.xacro：机身、12 个关节、脚、IMU、雷达和相机坐标系。
  display.launch.py：RViz 模型显示。

src/quadruped_control
  controllers.yaml：joint_state_broadcaster 和 12 关节轨迹控制器。
  joint_limits.yaml：关节限制。

src/quadruped_bringup
  bringup.launch.py：机器人模型、控制、感知、决策和速度门的统一公共入口。

src/quadruped_perception
  vision_obstacle_detector.py：轻量 OpenCV 障碍证据。
  terrain_analyzer.py：点云 TF、ROI、地形特征和 Nav2 障碍点云。
  topic_selection.py：多个默认传感器话题的锁定和超时切换。
  config/vision.yaml、terrain.yaml：感知参数。

src/quadruped_planning
  obstacle_crossing_manager.py：普通越障融合决策。
  cmd_vel_gate.py：双心跳速度保护。
  competition_obstacle_manager.py：Robocon 比赛状态机。
  course_waypoint_navigator.py：比赛障碍接近点与 Nav2 Action 桥接。

src/slam
  config/slam.yaml：SLAM Toolbox 参数。
  config/nav2.yaml：Nav2、代价地图、速度平滑和碰撞监控参数。
  launch/slam.launch.py：完整系统入口。
  launch/navigation.launch.py：精简 Nav2 入口。
  nav2_readiness_monitor.py：传感器和 TF 就绪后自动激活 Nav2。

scripts
  bootstrap.sh：rosdep 安装依赖。
  build.sh：统一 colcon 编译。


四、常用启动命令
----------------

每个新终端都先执行：

  source /opt/ros/jazzy/setup.bash
  cd ~/wakula
  source install/setup.bash

只显示模型：

  ros2 launch quadruped_description display.launch.py

启动模型、感知、越障决策和速度门，不启动 SLAM/Nav2：

  ros2 launch quadruped_bringup bringup.launch.py use_control:=false

启动完整 SLAM + Nav2 + OpenCV + 点云链路：

  ros2 launch slam slam.launch.py

无 RViz 启动：

  ros2 launch slam slam.launch.py rviz:=false

没有 RGB 相机时关闭 OpenCV：

  ros2 launch slam slam.launch.py vision:=false

指定非默认相机话题：

  ros2 launch slam slam.launch.py \
    camera_topic:=/my_camera/image_raw \
    point_cloud_topic:=/my_camera/points

只加载 Nav2 参数和节点，不自动激活：

  ros2 launch slam slam.launch.py rviz:=false nav2_autostart:=false

比赛模式：

  ros2 launch slam slam.launch.py competition:=true

启用 mock ros2_control：

  ros2 launch quadruped_bringup bringup.launch.py use_control:=true


五、启动前必须存在的真机数据
--------------------------

基础自主导航至少需要：

  /scan                  sensor_msgs/msg/LaserScan
  /odom                  nav_msgs/msg/Odometry
  map -> odom            SLAM Toolbox 产生
  odom -> base_link      状态估计器产生
  base_link -> lidar     URDF 或驱动静态 TF

OpenCV 辅助需要任一 RGB 图像候选话题。

点云地形和跨越高度判断需要任一 PointCloud2 候选话题，并且相机/雷达 frame 到
base_link 的 TF 可用。

真机运动需要 SDK 或控制器订阅最终 /cmd_vel，并理解 /crossing/mode 和
/crossing/action。若缺少点云，普通越障管理器会保持 STOP，这是预期的失效安全行为。


六、已经完成的工作
------------------

机器人模型与控制：

1. 建立通用 12 自由度四足 URDF/Xacro。
2. 增加 IMU、2D 雷达、RGB-D 相机坐标系。
3. 配置 mock ros2_control、joint_state_broadcaster 和 12 关节轨迹控制器。
4. 提供 RViz 模型调试入口。

SLAM 与 Nav2：

1. 接入 SLAM Toolbox 在线异步建图。
2. 配置 Nav2 全局规划、DWB 局部控制、恢复行为和行为树导航。
3. 精简未使用的路由、停靠等进程，统一启动职责。
4. 建立固定速度链：cmd_vel_nav -> smoothed -> terrain_safe -> cmd_vel。
5. 保证 Collision Monitor 是 /cmd_vel 唯一最终发布者。
6. 增加 Nav2 就绪监视器，等待实时雷达、里程计和定位 TF 后才激活。
7. 修复缺少 TF 时强制关闭可能触发的 Nav2 生命周期崩溃。

OpenCV 感知：

1. 使用 HSV 提取橙色和蓝色比赛障碍。
2. 使用灰度、Gaussian Blur、Canny 和轮廓几何补充无明显颜色的障碍。
3. 可识别 poles、height_bar、wall、colored_obstacle 四类证据。
4. 使用最近 5 帧至少 3 帧一致的投票减少单帧误检。
5. 默认 8 Hz、最大 640 像素宽，控制 RK3588 负载。
6. 支持多个常见相机默认话题，锁定一个来源并在失联后自动切换。

点云感知：

1. 自动接入常见 PointCloud2 话题。
2. 按消息时间戳转换到 base_link。
3. 使用 NumPy 完成有限值过滤、ROI 裁剪和有界降采样。
4. 通过分位数估算地面和障碍高度。
5. 通过最小二乘斜率和残差估算坡度、粗糙度及可通行度。
6. 同一份点云发布到 Nav2 local_costmap，辅助 2D 激光识别近距离立体障碍。
7. 支持点云源锁定和失联切换。

融合和安全：

1. 点云几何决定 WALK、STEP、CLIMB、STOP。
2. OpenCV 只能让 WALK 降速并等待深度确认，不能单独触发危险动作。
3. 高度阈值错误时恢复安全默认值。
4. 未知视觉类型、NaN、画面边缘或超时证据被拒绝。
5. 速度门同时检查导航命令和越障决策心跳，任一超时输出零速度。
6. Python 节点能处理 launch 与终端重复 SIGINT，关闭不再输出误导性 traceback。

比赛框架：

1. 根据 Robocon V1.0 建立 210 秒状态机。
2. 支持障碍提示、完成、失败、重试、计分、返回启动区。
3. 支持足端接触、有效距离和 T 字台阶进度检查。
4. 支持不按固定顺序完成障碍。
5. 提供比赛障碍接近点到 Nav2 NavigateToPose 的桥接。

工程质量：

1. 6 个 ROS 2 包可完整编译。
2. 当前 17 项单元和配置测试全部通过。
3. 完成合成 RGB + PointCloud2 端到端融合测试。
4. README、算法说明和完整通信合同已建立。


七、当前尚未完成的部分
----------------------

1. 没有接入具体品牌机器狗的 SDK。
2. 没有真实电机、编码器、IMU 和足端力传感器硬件插件。
3. STEP、CLIMB、LOW_PROFILE 等仍是动作请求，不是完整关节轨迹。
4. 没有 MPC、WBC、逆运动学或动态落脚点规划器。
5. 没有完整二维高程图、坡面分割和可落脚区域地图。
6. RGB 障碍框尚未与对应深度 ROI 做时间同步和空间关联。
7. OpenCV 阈值仍需使用比赛现场相机和光照标定。
8. course_waypoints.yaml 仍是占位坐标。
9. URDF 尺寸、质量、惯性和传感器外参仍需按真机测量。
10. 缺少完整 Gazebo/Isaac 仿真赛道和自动回归场景。
11. 缺少长期 rosbag、CPU、内存、温度和导航延迟测试。
12. 缺少硬件急停、驱动侧看门狗和故障恢复的系统级验证。


八、推荐后续开发顺序
--------------------

P0：先让真机安全跑起来

1. 确认机器狗品牌、SDK 版本、控制模式和通信方式。
2. 编写 SDK 适配节点或 ros2_control hardware plugin。
3. 发布稳定的 /odom 和 odom -> base_link。
4. 接入真实 /scan、RGB、PointCloud2 和传感器 TF。
5. 标定时间同步、相机内参、相机外参、雷达外参和 IMU 零偏。
6. 在驱动侧增加急停、命令超时、姿态限制和关节限位。
7. 只允许低速、架空或保护绳条件下首次联调。

P1：实现真正可执行的越障动作

1. 定义上层动作到控制器的明确协议，建议使用 ROS 2 Action 替代单纯字符串。
2. 为 STEP、CLIMB、LOW_PROFILE 分别实现动作状态机。
3. 接入足端接触和机身姿态反馈。
4. 增加动作接受、执行反馈、完成、失败和取消机制。
5. 越障动作期间锁定普通 /cmd_vel，完成后平滑交还 Nav2。
6. 对每种障碍建立最大高度、坡度、速度和姿态安全包络。

P2：完善 RGB 与深度融合

1. 使用 message_filters 同步 RGB 和深度/点云时间戳。
2. 将 OpenCV 障碍包围框投影到点云或深度图。
3. 对框内点云估算距离、宽度、高度和地面接触位置。
4. 增加连续跟踪 ID，避免同一障碍重复触发。
5. 使用 rosbag 收集误检和漏检，按现场数据调参。
6. 只有规则视觉无法满足比赛需求时，再评估学习模型。

P3：高程地图与落脚规划

1. 构建机器人周围局部高程栅格。
2. 区分地面、台阶边缘、坡面、坑洞和不可见区域。
3. 根据机身姿态和腿部工作空间生成候选落脚点。
4. 评价落脚点高度差、坡度、粗糙度、边缘距离和支撑多边形。
5. 将落脚序列交给 MPC/WBC，并根据接触反馈在线修正。
6. Nav2 继续负责远距离路径，高程/足步规划负责最后 1～2 米。

P4：比赛与仿真验证

1. 根据正式场地图纸更新 course_waypoints.yaml。
2. 创建全部比赛障碍的 Gazebo 场景。
3. 为每类障碍建立成功、失败、超时和恢复测试。
4. 校验比赛计分、接触规则和返回启动区逻辑。
5. 录制完整运行 rosbag，并建立可重复的离线回归测试。
6. 在 RK3588 上连续运行，记录 CPU、内存、温度和话题延迟。


九、建议的新接口方向
--------------------

当前 /crossing/action 是 String，适合原型，但真机动作建议新增 ROS 2 Action，例如：

  /execute_crossing
  Goal：障碍类型、估计高度、距离、目标速度、允许风险等级
  Feedback：当前阶段、进度、姿态、足端接触、失败原因
  Result：成功/失败、实际耗时、最终位姿、错误码

保留 /crossing/mode 和 /crossing/action 作为状态显示或兼容接口，真正动作通过 Action
完成接受、反馈、取消和结果闭环。新增接口时必须同步更新 com.txt。

十一、常见问题
--------------

问题：Nav2 一直没有激活。
检查：/scan、/odom 是否持续发布，map -> base_link 是否存在。查看
      nav2_readiness_monitor 日志中列出的 missing 项。

问题：terrain_analyzer 一直提示等待 TF。
检查：点云 header.frame_id 是否正确，该 frame 到 base_link 的 TF 是否存在，时间戳
      是否与 TF 同步。

问题：OpenCV 没有识别障碍。
检查：实际使用的图像话题、图像编码、HSV 范围、Canny 阈值、min_area_px；开启
      /vision/debug_mask 观察分割结果。

问题：视觉识别到了但没有 STEP/CLIMB。
说明：这是设计行为。视觉只能提前减速，STEP/CLIMB 必须由点云高度确认。

问题：机器人一直 STOP。
检查：/terrain/features 是否发布且点数足够；/crossing/speed_scale 是否有心跳；
      /cmd_vel_smoothed 是否持续发布。

问题：有多个相机话题但节点使用了错误的话题。
处理：通过 camera_topic 或 point_cloud_topic 显式指定；也可等待当前源超过 2 秒后让
      备用话题自动接管。

问题：关闭时出现 Ubuntu 崩溃报告。
检查：使用最新代码；Nav2 应在传感器和 TF 就绪前保持未激活。不要使用 kill -9，
      正常按一次 Ctrl+C 并等待进程清理。


十二、修改代码后的标准流程
--------------------------

1. 修改代码和配置。
2. 同步检查四份根目录文档：

  README.md              使用方式、目录或启动变化
  instruction.txt       模块职责、算法和调试原理变化
  com.txt               Topic、Action、Service、TF、字段或超时变化
  DEVELOPMENT_GUIDE.txt 已完成工作、已知限制和后续路线变化

3. 编译和测试：

  source /opt/ros/jazzy/setup.bash
  ./scripts/build.sh
  source install/setup.bash
  colcon test --event-handlers console_direct+
  colcon test-result --verbose

4. 检查差异：

  git status -sb
  git diff --check
  git diff --stat

5. 当前项目约定直接提交并推送 main：

  git switch main
  git pull --ff-only origin main
  git add 明确的文件列表
  git commit -m "简洁说明本次修改"
  git push origin main

推送前必须确认工作区没有无关文件，测试通过，且 README.md、instruction.txt、com.txt
和 DEVELOPMENT_GUIDE.txt 与代码保持一致。不得使用 git push --force 覆盖 main。


十三、交接完成标准
------------------

一个新开发者能够完成以下事项，才算已经基本接手：

1. 独立编译 6 个包并运行全部测试。
2. 解释 map、odom、base_link 和传感器 frame 的关系。
3. 说明 /scan、/odom、RGB 和 PointCloud2 分别被哪些节点使用。
4. 说明 OpenCV 为什么不能单独触发 CLIMB。
5. 说明 /cmd_vel 的完整链路和每一层安全职责。
6. 使用合成消息或 rosbag 验证 vision、terrain 和 crossing 输出。
7. 找到所有主要参数所在 YAML 文件。
8. 知道 SDK 适配层需要订阅和发布哪些接口。
9. 修改接口后同步更新 com.txt。
10. 验证通过后将代码直接推送到 main。
